# 同一對話中的任務追問候選

Swift 只顯示對話與傳送輸入。Rust server 負責識別任務、保存來源與核對修訂。
CLI 或其他介面使用相同的 `HumanAction::Submit`，不需要另寫關聯邏輯。

## 使用方式

- 傳送「任務 A：讀 README.md」。再傳「再詳細一點」，補充 A。
- 傳送「A」或「A 的進度」，查詢 A，並把接續對象設為 A。
- 傳送「A 用條列整理」，直接補充 A。
- 同時建立 A、B 後，傳送「用表格整理」。server 先問對象。回覆「B」才補充 B。
- 在澄清期間要另開工作，使用「任務 C：需求」。未知名稱不會建立新任務。

目前支援詳細、簡短、條列、表格、繁體中文與英文這些輸出調整。
其他新要求仍可使用「補充 A：要求」或「修改 A：要求」。
這是有限的自然追問候選。它不是完整自然語言理解，也不代表 D02 已接受。

## 關聯規則

Rust 使用同一個 server 資料庫內的 `chat_conversation_context_v1` 設定。
它只保存目前 chat 身分、原始 Human 事件識別、時間、任務識別及修訂。
它不另存訊息正文，不供模型檢索，也不啟用模型記憶。

每次讀取都重查原始 Human 事件及已保存的結果。
工具或模型事件不能設立這個對象。
只有成功的單任務 Human 對話可以讓下一句直接補充。
多任務對話、缺少對象、過期或已變更的修訂均先澄清。
待澄清的要求仍讀自原始 Human 事件。後續選擇須符合當時候選的修訂。

紀錄在 30 分鐘後失效。
沒有單一可接續結果的 Human 控制、記憶操作或配對身分切換會中斷隱含對象。
記憶查詢與記憶語法澄清也屬於話題切換。
重送舊來源不會取代較新的對象，也不會再次套用補充。
紀錄在路由前先取出。中途退出可能需要重新指定任務，但不會沿用舊對象。
重啟後仍須通過來源、身分、時間與修訂核對。

Rust chat 會在本機 journal 保存一筆話題標記，內容只有原始來源 UUID。
下一個任務訊息與 `conversation_boundary` 會在同一個交易內排隊，先送界線，再送訊息。
server 只清除對話對象，不取消、批准或完成任務，也不保存記憶正文。
舊界線的來源重送不會清除較新的對象。executor 身分不能送出這種 Human 事件。
本機重啟會保留待送界線。一般佇列沒有空間時，任務輸入與界線一起回滾。
記憶刪除只需保存話題標記，不占一般待送空間，仍沿用原本的獨立刪除限制。
背景記憶同步不會新增界線。不同步更新的舊 server 會拒絕未知事件，不會改成模型任務。

## 對話程式版本與連線

Rust chat 收到 Welcome 後，先送出 `conversation_ready`，版本為 `1`，再送出 journal 的待送訊息。
其他介面可使用相同的 Rust 連線與契約。Swift 不處理此判斷。
server 只接受目前 chat 身分、目前連線世代與有效租期的宣告。
版本不符、缺少宣告、資料格式錯誤、地端 executor 身分或過期連線，均不能取用或保存隱含對象。
未宣告的舊 chat 仍可明確查詢與控制任務。省略對象的補充會先澄清；請使用「補充 A：需求」完成明確修改。

能力資料存在原本的 settings，只有版本與連線世代，沒有訊息正文或批准。
歷史資料不會自動成為新連線的能力；每次連線都須重新宣告。
同版本重新連線可保留經來源核對的對象。中途若有未宣告的 chat 連線，下一個 chat 不得繼承舊對象，即使舊程式沒有送出 Human 訊息。
server 的故障恢復會增加世代並重設對象；之後須重新指定任務。原任務、來源、費用與未知結果的處理規則仍保留。

新版 chat 必須連到支援此控制 frame 的 server。舊 server 會拒絕未知 frame，不會降級猜測任務。
這是 server 對舊 chat 的限制與新版宣告候選。完整版本協商、安裝與升級仍待驗收。

補充沿用原本的任務識別、工具範圍、授權來源、費用計數及期限。
它透過既有 `Command::Revise` 撤銷舊 run 與批准。
未知工具結果仍交由既有核心核對，不因文字補充而變成成功。
查詢與澄清不呼叫模型，也不建立費用預留。

## 驗證範圍

回歸案例位於 `crates/pulse-link/tests/conversation.rs` 與
`crates/pulse-link/src/memory_chat/topic_tests.rs`。
它們直接使用認證後的 Rust server 入口，涵蓋雙任務隔離、修訂、模型 context、
重啟、舊來源重送、工具事件、澄清後選擇、過期、記憶話題切換與瀏覽器範圍。
另有真正 Rust 命令迴圈與 WebSocket 案例，核對查詢記憶、追問、澄清與選擇後的單次修訂。
版本案例另核對未宣告、錯誤版本、舊世代、過期、撤銷、錯誤角色與損壞資料。
重新開啟案例使用 Store 與 Hub，重新宣告後才恢復待澄清內容；它不是桌面程序重啟驗收。
另有 server `recover` 後要求重新指定任務，以及舊程式未送訊息仍不能傳下舊補充內容的案例。

這些是元件測試。完整 SwiftUI 操作、兩家 provider 的實際回答、中文輸入、
效能與長時間運作仍依 D01–D10 驗收，不由本文件或收件回覆替代。
