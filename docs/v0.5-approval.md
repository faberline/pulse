# v0.5 操作批准核心

工作單：[#22](https://github.com/faberline/pulse/issues/22)。這是 [日常助理 D05](dot-parity.md) 的持久授權基礎。效果仍只允許 `fixture:` target，尚未接上產品的操作卡片、browser 或 computer 派工。

## 提議與批准

`OperationProposal` 保存 request ID、完整 run token、target、intent 與期限。提議必須原樣存在於已保存、已套用並關聯同一 task 的 Tool 事件。比較及 digest 使用 canonical JSON，因此欄位順序與等值數字表示不會改變身分。

`Store::propose_operation` 在同一交易保存提議並將 Planning 改為 WaitingApproval。同一 task 最多一項當前提議，歷史最多 32 項。等待不增加模型次數、工具次數或預留費用。重播只回傳原紀錄，不更新期限或批准。

人類透過 `ApproveOperation` 或 `RejectOperation` 命令處理提議。`OperationBinding` 包含 task ID、expected revision、request ID 與完整提議 digest。批准者來自已認證的 Human 事件及 server owner 設定，不能由 payload 指定。

| 提議狀態 | 意義 |
|---|---|
| pending | 等待人類決定，task 為 WaitingApproval |
| approved | 已批准，task 為 Ready，尚未執行效果 |
| rejected / withdrawn | 人類拒絕或撤回，task 為 Blocked |
| expired / invalidated | 到期，或任務／run 已改變；不得執行 |
| dispatched | 批准已消耗，效果結果須由 operation／receipt 核對 |

## 派工與恢復

`Store::prepare_approved_operation` 會重新核對提議來源、人類批准命令及其 outcome、owner、digest、revision、epoch、scope、期限與工具上限。來源內容被移除後，即使舊的批准 metadata 還在，也不能派工。

在同一交易中，它消耗批准、保存穩定的 operation ID／idempotency key、把 operation 設為 Unknown，再增加一次工具計數。外部效果由交易外的 adapter 執行。重播或同一批准的第二次派工被拒絕。原 `prepare_operation` 保留既有模擬行為，但已使用批准流程的 run 不能改走舊入口。

修改、取消、完成、重啟、重新領取 run，或 local 結果清掉原 run 時，未消耗的批准會失效。到期事件各有自己的持久通知。排程沒有新工作可領取時，仍能回報狀態變更。

已派送後的拒絕不能假裝撤回效果。沿用取消、OutcomeUnknown、原 operation receipt 與 reconciliation。重啟時，先呼叫 `recover` 再恢復派工；server 的 remote 啟動流程已有此呼叫。尚未執行的舊批准保持 Blocked，等待新的有效提議及人類決定。

這個 library 的呼叫者是受信任應用程式。實際對話認證、local capability、裝置 lease、網路範圍與執行前畫面核對仍由後續整合負責。此階段不能放行真實寫入或宣稱 D05 已接受。
