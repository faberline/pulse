# 排程候選

這是 D07 的實作候選。Swift 仍只負責介面。時間解析、來源、排程、取消、派工與通知都由 Rust 處理。
目前支援單次提醒與單次定時工作。它不代表完整 D07 或日常助理目標已通過。

## 在同一對話框使用

- `10分鐘後提醒我喝水`
- `明天上午9點提醒我看進度`
- `排程 A：明天09:00：執行 分析 Pulse`
- `排程 B：2026-11-03 09:00 Asia/Taipei：提醒 查看結果`
- `查詢排程`
- `查詢排程 A`
- `取消排程 A`

「提醒」只傳送原文字，不啟動模型或工具。「執行」建立一個有界新任務，沿用既有 remote executor、費用與工具限制。
它不能直接改動既有任務、記憶或再次建立排程。電腦視窗選擇不可預存到未來使用。瀏覽器操作仍需到期後取得新來源與逐次批准。

時間預設為 `Asia/Taipei`。支援秒、分鐘、小時與天的相對時間、今天／明天／後天，以及含日期的本機時間。
可用 IANA 時區名稱或含偏移的 RFC3339 時間。夏令時間產生重複或不存在的時間時，拒絕猜測，須改用明確偏移。
時間、名稱或動作不明時會澄清，不會落入立即執行的一般任務。

## 來源與執行

Rust chat 在本機保存輸入時，將相對時間轉為固定 UTC 到期時間。重送及重開沿用原要求，不從重連時間重新計算。
原文字與固定要求保存在同一私有 journal 的輸入紀錄中。server 再用原文字與提交時間重算核對。
server 保存不可變的 Human 來源事件、範圍、時區與要求。工具或外部內容不能建立、取消或變更排程。

到期由計時器喚醒。無排程時等待變更；未到期時等待最近時間或變更。容量不足時只做有界的資料庫重試，不呼叫模型。
尚未處理完的持久事件先於到期工作。到期交易再次核對原 Human 事件與完整要求。
同一交易保存處理狀態、確定的任務識別與通知。並行計時器、重送及正常重啟不會重複開工。

等待到期不占任務工作名額。定時任務的 15 分鐘期限從原到期時間起算，不因延後派工而延長。
若工作建立要求到達 server 時已超過到期時間，或重啟時已超過工作期限，標為未執行並要求新指示。
提醒可在重連後補送，並顯示原定時間。取消與到期以交易順序處理。已建立的任務不因停用排程而被刪除或冒稱已取消。
離線取消只是待送要求；server 確認前不能宣稱取消已生效。

## 通知與恢復

到期通知使用獨立的 `ScheduleNotice` 傳輸，不當作可合併的進度快照。
只交接給有效 chat 連線，而且該連線須宣告 `ScheduleReady`。executor 不能宣告或保存 chat 通知。
持久交接與 outbox 確認在同一交易。尚未交接的通知不受一般快照游標略過。
新連線先重新宣告能力；未支援通知的連線不會消耗新的到期通知。

Rust chat 先保存通知，再確認傳輸。重複識別必須有相同內容；不同內容會拒絕。
快照更新不會清除通知紀錄。重開後能再次顯示同一通知，不會重複保存。
介面可從 `NativeState.schedule_notices` 取得已核對的結構資料；目前也會顯示在同一對話中。
傳輸確認只代表已保存，不代表使用者已讀。

### 原生通知顯示候選

在設定開啟「在這部 Mac 顯示提醒通知」時，Swift 才向 macOS 請求通知權限。
獲准後，Rust 在目前 chat 的私有 journal 保存啟用時間。server、executor 或模型不能開啟這個選項。
只有啟用後到期、距到期未滿 24 小時的新提醒能成為通知。過期、未啟用時已保存的提醒仍可在對話查看，不會突然補跳整批舊通知。

Rust 在同一個接收交易建立通知候選，再先提交一筆顯示要求，才交給介面。
同時只交出一筆。要求包含 Rust 決定的文字、嘗試識別與綁定 server／device／notice 的系統識別。
Swift 只呼叫系統顯示介面，並回報「已交給系統」、「拒絕」或「失敗」。Swift 不解析時間、不建立持久佇列，也不決定重試。
重複畫面狀態在同一 Swift process 不會重複呼叫系統。Rust 保存相同嘗試的回覆；矛盾或未知回覆不能改寫紀錄。

若顯示要求已交接而回覆遺失，重開 Rust chat 時改列「待核對」。即使系統通知已被關閉，也不會自動再跳一次。
同一次執行中超過 30 秒未收到回覆，也改列待核對，讓下一筆提醒可繼續。晚到回覆不能將這種未知狀態改稱成功。
這保證不自行重做未知的顯示效果，並不保證每筆要求都產生橫幅。原文與未確認數量仍會顯示。
macOS 的專注模式、通知設定或 app 關閉可能使通知未顯示。「已交給系統」不代表已顯示或已讀。
停用會抑制尚未交出的通知。已交給系統的顯示不會被撤回。重新啟用不會重新排送先前未確認的通知。
通知被系統拒絕時，Rust 關閉這個本機選項；須由使用者重新啟用。

通知狀態仍在同一 SQLite，最多每個已保存提醒一筆，沿用 1,000 筆上限。schema 13 不新增程序或外部服務。
Rust 契約與 Swift 替身測試核對重開、去重、拒絕、停用、期限、交易回滾與原文字。
這些測試沒有請求真實通知權限，也沒有展示系統橫幅。真正 macOS 點選啟用、背景顯示、拒絕後恢復與關閉 app 流程仍待實機驗收。
權限流程依 [Apple 通知授權文件](https://developer.apple.com/documentation/UserNotifications/asking-permission-to-use-notifications)：在顯示前重新核對系統權限。這份文件不是本機橫幅已通過的證據。

## 上限與剩餘驗收

最多 100 筆等待排程、1,000 筆排程歷史、1,000 筆本機固定輸入與 1,000 筆本機通知。
提醒文字最多 1,024 bytes，工作最多 4,096 bytes，時間最多距提交 366 天。
滿額不會自動丟棄歷史或取消證據；查詢與停用仍可使用。期限、每日 US$1、每任務 US$0.25 與未知費用處理均保留。
schema 12 新增同一 SQLite 內的排程與地端傳送資料，不新增服務或另一套任務真相。

測試包含 Core 交易、真正 loopback WebSocket、Rust chat 重開、相對時間凍結、較早計時器喚醒、取消、過期、容量、錯誤授權、通知交接回滾與重送。
沒有設定 provider 的定時工作會保持未完成，不能把派工當作成功。

仍需驗證真正 SwiftUI 流程、原生系統通知顯示與權限、兩家 provider 的完整定時工作、事件訂閱，以及保留期限與正式還原。
一般備份檢查仍只產生隔離候選。不能將舊 server 資料庫當作可直接恢復執行的排程狀態。
尚未驗收重複日曆排程、關閉 app 後的桌面通知與長時間運行。當前 head CI 也必須通過。
完整 D01–D10 目標保持進行中。
