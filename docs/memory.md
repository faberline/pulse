# 記憶儲存候選

這是 D06 的候選。已接進單一 SwiftUI 對話框與 Rust 傳送程序，尚未將記憶加入模型回答。
它不代表 D06 已通過。

## 已實作

在同一個對話框輸入：

- `記住 回答語言：繁體中文`
- `查詢記憶`
- `更正記憶 回答語言：簡短的繁體中文`
- `忘記記憶 回答語言`
- `取消待送記憶 回答語言`

名稱與內容不明時先說明格式，不建立一般任務。
記憶卡片顯示目前內容、來源時間與到期日。
「修正」與「忘記」只填入對話框，仍須由人類送出。

- `Store::change_memory` 只接受可信入口指定的 `Origin::Human`。工具與外部來源均被拒絕。記憶不能建立任務或授權操作。
- 每筆保留一份目前標題、正文、隨機來源識別、來源時間與修訂。來源正文不另寫入通用任務事件或聊天紀錄。
- 新增、修正與刪除都有來源識別。相同來源重送不再新增，也不延長期限。相同來源帶不同內容時拒絕。
- 期限是來源時間加 90 天。修正需指定目前修訂，並提供新的人類來源。舊修訂與舊來源的內容指紋會移除。
- 最多 100 筆有效記憶。標題最多 128 個 UTF-8 bytes，正文最多 1024。新增與修正共用 10,000 筆來源上限；到上限後仍可刪除現有記憶。
- 查詢或改動前清除到期內容。已到期內容不能因時鐘回退而重新可見。server 運行時也會在期限到達時清除，新記憶會喚醒維護程序重新計時。

## 刪除與還原限制

資料庫旁有 `<database>.memory-restrictions.json` 與 `<database>.memory-lock`。
兩個檔案僅限資料庫擁有者使用。程式拒絕符號連結、硬連結與開放給其他使用者的權限。
多個 Store 以檔案鎖避免互相覆寫限制；短暫衝突最多等待 250 毫秒，仍忙碌時拒絕本次要求，不搶走別人的鎖。

限制檔只保留 keeper 識別、遞增序號、不能恢復的記憶識別與修訂、撤銷來源 UUID，以及有效取消要求的重送證據。
它沒有標題、正文或可識別內容摘要。
修正、刪除與到期會先將限制檔原子替換並同步到磁碟，再改動 SQLite。
若中途失敗，下一次開啟或記憶存取會先套用限制。
修正若在限制落盤後失敗，舊內容仍會刪除；新內容可能未保存。未成功回覆時須重新查詢。

SQLite 使用 `secure_delete=ON`。成功回覆前會核對 WAL 截斷的結果。
這會移除目前資料庫與 WAL 的適用內容，沒有承諾清除 SSD 歷史區塊、檔案系統快照或備份。
刪除仍保留無正文的重送證據，防止舊要求讓內容復活。
即使還原的資料庫早於原來源，撤銷證據也會先建立無正文的來源紀錄，阻擋晚到要求。
UUID 的大小寫、緊縮、括號與 URN 寫法視為同一來源；舊來源指紋仍以原寫法核對。
若舊資料包含互相衝突的 UUID 別名，升級會拒絕，不會任意丟棄其中一筆。

資料庫已綁定 keeper 後，缺少限制檔、keeper 不符或限制序號比資料庫舊，均拒絕開啟。
還原資料庫時必須保留**目前**限制檔。不能把舊限制檔當成備份的一部分一併還原。
若資料庫和限制檔一起回退到同一個舊版本，程式無法單憑這兩個舊檔證明還原的限制最新。
已有隔離的備份檢查工具，但尚無正式還原切換入口；見 [備份候選](backups.md)。

資料庫 schema 已升至 8。先前最高支援 schema 7 的 Pulse 會拒絕開啟。
升級後不得刪除限制檔以繞過檢查。
舊格式限制檔會先從目前資料庫補齊已刪來源 UUID，再升至格式 2。
若舊還原檔已缺少這些來源證據，升級會拒絕。不能把未知來源當成已安全撤銷。

## 驗證與剩餘工作

### 對話傳送與地端副本

記憶使用已配對的 chat 身分存取 `GET/POST /v1/memories`。
executor 與未驗證入口不能讀寫。
回覆標示 `Cache-Control: no-store`，客戶端拒絕重新導向與超過 1 MiB 的回覆。
記憶正文不寫入一般 task、事件、聊天或有序訊息 outbox。
地端的 `local_memory_queue` 與 `local_memory_cache` 只是同一 SQLite 的傳送／快取資料；Core 仍是唯一記憶真相。

離線新增會保存原來源 UUID 與時間，不宣稱 server 已保存。
修正需先有已核對的記憶名稱與修訂，再凍結該修訂排隊。
「忘記」可指定已核對的來源，或同名的待送新增／修正。
「取消待送記憶」只撤銷同名待送來源。若修正從未送達，原先已確認的內容會保留。
若 server 已保存該來源但確認回覆遺失，取消仍會移除該來源。已被修正取代的舊內容不會復活。
沒有可核對或待送來源時，要求不保存，草稿保留。
新增與修正最多待送 100 筆。刪除與取消另有 100 筆保留空間，查詢不占用這兩種名額。
刪除與取消先送出。原待送正文先從本機清除，只保留無正文的來源撤銷要求，直到 server 確認。
server 另保留 10,000 個尚未見過的來源撤銷名額。此名額用盡時仍可刪除已知來源。
所有來源撤銷與有效取消回覆證據都有上限；不以無限制紀錄換取重送能力。
重送同一筆有效取消會回覆原結果。沒有新增撤銷的空操作不另保存取消收據。

排隊修正或刪除會先清除本機該份快取與舊來源的待送副本。
重連時，先讀取 server 目前刪除限制，清除對應舊來源，再重送剩餘要求。
成功或明確拒絕後清除待送正文，只保留無內容的來源與結果標示。
ACK 遺失時重送同一來源，不改時間，也不延長 90 天期限。
提交後若清除檢查仍忙碌，server 回傳可重試狀態，不將已提交的要求誤判為永久拒絕。
舊修訂若已被別的人類來源改動，拒絕本次修正，不重新指向新修訂。
刪除也不會改指向新的獨立人類來源；介面會提示重新查詢。

本機快取不證明目前遠端狀態。離線介面會標示可能已變更。
程序重新啟動時先清空來源正文快取，重新連線核對後才顯示，防止舊本機資料庫還原後離線顯示已刪內容。
已凍結的待送要求保留，重連後仍先套用刪除限制。
來源到期時也會清除地端正文並截斷 WAL。
尚不能宣稱所有已撤銷或長期關閉的地端副本都已同步清除；完整 K15 仍未接受。

`tests/memory.rs` 核對人類來源、重送、期限、修訂衝突、容量、檔案權限、同時寫入、SQL 失敗與還原舊資料。
還原測試使用 [SQLite `VACUUM INTO`](https://www.sqlite.org/lang_vacuum.html) 產生一致快照。
它是測試用的未加密檔，不是產品備份功能。
檔案鎖採用 [Rust `File::try_lock`](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock)。

D06 仍需受限的模型 context 引用、刪除時的任務撤銷與衍生內容清除、已撤銷／關閉地端副本的完整清理，以及正式還原切換。每日加密備份、期限計時與隔離檢查已接上 server；容量與停機保留上限見 backups.md。
這些接妥前，不將記憶加入模型提示或聊天歷史。
K15 的完整任務保留與備份要求仍未完成。

`memory_chat::tests` 已核對真正 HTTP、原生指令迴圈、零 task／模型工作、草稿拒絕、ACK 遺失後先清除再重送、修訂衝突、重啟快取清空、角色限制及舊客戶端不回退成任務。
`tests/memory_revocations.rs` 另核對晚到來源、早於來源的還原、程序直接退出、舊格式升級與拒絕、來源別名、容量及較新內容保護。
Swift 測試另核對來源期限與舊狀態解碼。
實際畫面、供應商回答與目前 head hosted CI 仍待驗證。
